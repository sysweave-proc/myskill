### 本段抓到的三个工程点

> 说明：本节站点图在「还账」轮次中做过修正。原先把 `InitProcessGlobals()` 与 `InitProcess()`
> 的调用位置画错了，已按 `backend_startup.c` 的实际链路更正，详见 §5.1。

**① 槽位必须在 fork 之前分配** —— `postmaster.c:3589-3593` 的注释写得很直白：

> Allocate and assign the child slot. Note we must do this before forking, so that we can handle failures (out of memory or child-process slots) cleanly.

含义：`AssignPostmasterChildSlot()` 放在 `fork()` 之前，这样「没有空闲槽位 / 内存不足」这类失败可以在**父进程里**干净地处理掉，
而不必先 fork 出一个注定失败的孩子再收拾残局。这是「先占资源、后做不可逆动作」的标准写法。

**② 连接过多时 fork 的是「死胡同子进程」** —— `postmaster.c:3599-3611`：
槽位拿不到时不是直接拒绝，而是 `AllocDeadEndChild()`，起一个专门用来回错误消息的进程。
好处是错误信息的回送走的是**统一的子进程路径**，父进程不必为「还没进协议就出错」单独写一套通信逻辑。

**③ `fork_process()` 里先屏蔽信号再 fork** —— `fork_process.c:59-66`：
子进程继承的是一套「信号被屏蔽」的状态，等它自己装好 handler 再解除屏蔽，避免继承到 postmaster 的 handler 而丢掉关键控制信号。

## 2. C2 内存模型：站点图

### 2.1 起点

```
MemoryContextInit()                     utils/mmgr/mcxt.c:362
  ├─ TopMemoryContext = AllocSetContextCreate(NULL, "TopMemoryContext", ...)   :369
  ├─ CurrentMemoryContext = TopMemoryContext                                   :377
  └─ ErrorContext = AllocSetContextCreate(TopMemoryContext, 8K, 8K, 8K)        :392
       └─ MemoryContextAllowInCriticalSection(ErrorContext, true)              :397
```

调用时机：`main.c:114`（在几乎一切子系统之前），注释 `mcxt.c:353-357` 说明
普通多进程模式下**只有 postmaster 会调用一次**，子进程靠 `fork` 继承已经初始化好的上下文体系。

**为什么 `ErrorContext` 是最后一步？** `mcxt.c:389` 的注释给出理由：

> This should be the last step in this function, as elog.c assumes memory management works once ErrorContext is non-null.

即报错系统自己也需要内存，所以它依赖的上下文必须最后建——**先有能报错的能力，才能安全地做后面的事**。

`ErrorContext` 固定 8K 且允许在 critical section 内分配（`:394-397`），
目的是「即使别处 OOM，报错也还有内存可用」（`README:253-258`），
从而把 OOM 降级成可恢复的 `ERROR` 而不是 `FATAL`。

### 2.2 全局知名上下文一览

来源：`utils/mmgr/README`（官方设计说明，强烈建议原样读一遍）。

| 上下文 | 生命周期 | 说明 | README |
| --- | --- | --- | --- |
| `TopMemoryContext` | 永久 | 上下文树的根，等价于 `malloc`；**避免在其上运行 `CurrentMemoryContext`** | :185 |
| `PostmasterContext` | postmaster 级 | backend 起来后可删除，以释放继承来的 postmaster 内存 | :194 |
| `CacheMemoryContext` | 永久 | relcache / catcache 的常驻存储 | :204 |
| `MessageContext` | 单条消息 | **`PostgresMain` 外层循环每轮开头 reset** | :214 |
| `TopTransactionContext` | 顶层事务 | 跨子事务的状态管理信息 | :223 |
| `CurTransactionContext` | 当前事务 | 顶层事务时等同上一行；子事务时指向子上下文 | :232 |
| `PortalContext` | 单个 portal | 并非独立上下文，而是指向当前活跃 portal 上下文的全局变量 | :248 |
| `ErrorContext` | 永久 | 错误恢复专用，错误处理完即 reset | :253 |

> 注意 `MessageContext` 的 reset 时机 —— 这与 `00` 篇 §5 观察到的
> `tcop/postgres.c:1195-1204`「为每个 parsetree 单独建上下文」是同一套设计思路的两处体现。

### 2.3 分配路径与多态

```
palloc()                                utils/mmgr/mcxt.c:1390
   └─ 打到 CurrentMemoryContext 上
        └─ 具体分配由上下文类型决定（函数指针分派）
             AllocSetContextCreateInternal()   utils/mmgr/aset.c:347
             MemoryContextCreate()             utils/mmgr/mcxt.c:1152
```

四种上下文实现（`README:471-496`）：

| 实现 | 适用场景 |
| --- | --- |
| `aset.c` `AllocSetContext` | **默认通用分配器**，块大小可配置 |
| `slab.c` `SlabContext` | 固定大小 chunk，密集打包、减少碎片 |
| `generation.c` `GenerationContext` | 成组同寿命分配 / 近似 FIFO，不复用已释放空间 |
| `bump.c` `BumpContext` | 只分配不单独释放，无 chunk 头，最省空间 |

**多态机制**（`README:370-435`，这段是全篇最硬核的部分）：
- `MemoryContextData`（见 `utils/memnodes.h`）是「抽象基类」，行为由 `methods` 指针决定。
- 每个 chunk 前面紧贴一个 `uint64`，**最低 4 bit 存方法 ID**，用它在 `mcxt_methods[]` 里查到该用哪套方法。
- `pfree` 因此不需要额外参数就知道该调谁的 `free_p`：`MCXT_METHOD(pointer, free_p)(pointer)`。
- 其余 60 bit 编码 chunk 大小与到 block 的偏移；两者各需 30 bit，但因偏移必然 8 字节对齐，
  最低位恒为 0，于是**共用 1 bit**，合计 59 bit 够用。

> 这套「header 位域复用」设计是纯性能与空间的取舍产物，读 `memnodes.h` + `memutils_memorychunk.h` 时重点看这里。

### 5.1 两处原判断的错误与更正

**错误 1：`InitProcessGlobals()` 不是由 `SubPostmasterMain()` 调用的。**

正确路径：`postmaster_child_launch()` 的子进程分支（`launch_backend.c:241`）调
`InitPostmasterChild()`（`miscinit.c:96`），再由后者在 `:110` 调 `InitProcessGlobals()`。
`SubPostmasterMain()`（EXEC_BACKEND 路径）在 `launch_backend.c:620` 同样调 `InitPostmasterChild()`——
**两条路径在此汇合**。

**错误 2：`InitProcess()` 不在 `BaseInit()` 之下，两者不是嵌套关系。**

正确关系：`InitProcess()` 由 `BackendMain()`（`tcop/backend_startup.c:116`）在
**调用 `PostgresMain()` 之前**（`:124`）执行；`BaseInit()`（`postgres.c:4345`）与
`InitPostgres()`（`postgres.c:4379`）都在 `PostgresMain()` **内部**。

原来的写法把「并列的先后关系」误写成了「父子嵌套关系」。更正后的完整顺序：

```
BackendMain → InitProcess → PostgresMain → BaseInit → InitPostgres → InitProcessPhase2
```

注意 `InitProcess()` **先于** `PostgresMain()`——这与 `04` 篇强调的
「先有 `PGPROC` 才谈得上 LWLock」是同一件事：主循环一开跑就需要取锁。

### 5.2 `MyProc` 与 `PGPROC` 数组的关联（`proc.h:507-511`）

```c
/*
 * Accessors for getting PGPROC given a ProcNumber and vice versa.
 */
#define GetPGProcByNumber(n) (&ProcGlobal->allProcs[(n)])
#define GetNumberFromPGProc(proc) ((proc) - &ProcGlobal->allProcs[0])
```

**没有查找表、没有哈希——编号就是 `ProcGlobal->allProcs` 数组的下标，转换是纯指针算术。**
于是 `MyProc` 与 `MyProcNumber` 只是同一个东西的两种表示：

- 跨进程传递用**指针**（共享内存地址在各进程里都有意义）
- 需要索引镜像数组（如 `pgxactoff`）或做原子操作时用**编号**（整数更紧凑）

`PGPROC` 内部还有一个反向指针 `procgloballist`（`proc.h:191`），指向它所属的 free list——
这正是 `04` 篇 `:467` 那条 `Assert` 校验的字段。
