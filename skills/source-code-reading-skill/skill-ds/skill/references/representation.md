# 表达选择 · Representation

## 选择流水线（顺序不可颠倒）

```text
核心问题
   ↓
主导模式
   ↓
表达族
   ↓
具体方法
   ↓
渲染器 / 工具
```

**关键规则不是"Mermaid 优先"，而是"语义方法优先，渲染器第二"。**

## 表达族

| 表达族 | 什么时候用 | 什么时候别用 |
|---|---|---|
| Entity/Relationship | 对象拓扑是主要难点 | 运行时顺序才是主要问题 |
| Management/Ownership | 所有权/管理/资源控制是核心 | 只知道一个指针关系 |
| Flow/Control | 执行路径与分支结构重要 | 调用只是依赖关系 |
| State/Lifecycle | 状态或对象生命是核心问题 | 只关心静态结构 |
| Sequence/Interaction | 多个角色随时间交互 | 单条线性例程就够 |
| Data/Dataflow | 数据传播/变形重要 | 问题只在控制顺序 |
| Concurrency/Sync | 共享状态 + 同步重要 | 锁只是偶然出现 |
| Architecture/Layer | 子系统边界与系统位置重要 | 主题太局部 |
| Recovery/Failure | 失败会改变系统状态 | 只讲正常路径 |
| Memory Layout | 偏移/对齐/缓存行几何重要 | 概念关系已足够 |

## 渲染器取舍

| 选择 | 条件 |
|---|---|
| Mermaid | 概念性图、节点少、要可版本化文本、Markdown 是交付面、几何布局不承载语义 |
| Graphviz 等布局引擎 | 图较大、自动连线路由重要、布局质量压过书写便利 |
| 静态分析输出 | 需要精确的 CFG/AST/数据流/调用图/依赖事实；图是机器导出的；源码级精度比手绘可读性更重要 |
| 表格或散文 | 关系图很小；节点多但语义简单；画图只会重复文字 |
| 手工精修图 | 视觉构图本身就是解释的一部分；需要出版物级版式；形式记号或几何重要而渲染器保不住 |

## 粒度

核心视图目标 **5–12 个主要节点**。图太大时**拆成 context / core / detail 三张**，而不是把每个标签缩小。

## 图 / 文 / 代码 的分工

```text
图   → 空间与时间关系
文   → 语义、条件、后果
代码 → 证据与导航
```

图不承担语义定义，文字不承担拓扑，代码不做结论。

## 警示

- **Mermaid 永远不是语义权威。** 一张 `flowchart` 可以渲染精心整理的控制视图，但不能因为它长得像就称它为形式 CFG。
- 表达方法可以来自历史（结构图、NS 图、HIPO、DFD、状态图、Petri Net 等），但**贴标签要基于语义，不基于外观**。
- 图是可选项。判断标准只有一个：**它是否降低了读者的认知负荷。**
