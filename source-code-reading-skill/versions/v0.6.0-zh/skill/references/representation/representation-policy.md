# 表达规范

## 选择流程

```text
核心问题
   ↓
主导 Pattern
   ↓
表达族
   ↓
具体图表方法
   ↓
Renderer / 工具
```

## 表达族

| 表达族 | 适用场景 | 避免使用的场景 |
|---|---|---|
| Entity/Relationship | 对象拓扑是主要难点 | 运行时顺序才是主要问题 |
| Management/Ownership | ownership/管理/资源控制是核心 | 只知道存在指针关系 |
| Flow/Control | 执行路径和分支结构重要 | 调用只是依赖关系 |
| State/Lifecycle | 状态或对象生命周期是核心问题 | 只关心静态结构 |
| Sequence/Interaction | 多个角色随时间发生交互 | 一个例程已经足够说明问题 |
| Data/Dataflow | 数据传播/转换很重要 | 问题只有控制顺序 |
| Concurrency/Sync | 共享状态 + 同步很重要 | 锁只是偶然出现 |
| Architecture/Layer | 子系统边界和系统位置重要 | 主题粒度过于局部 |
| Recovery/Failure | 失败会改变系统状态 | 只有正常路径 |
| Memory Layout | offset/alignment/cache-line 几何关系重要 | 概念关系已经足够 |

## Mermaid 与专业/手工方法的选择

### 优先使用 Mermaid，当

- 图是概念性的；
- 节点数量较少；
- 文本版本控制有价值；
- Markdown 是交付载体；
- 精确的几何布局不是语义的一部分。

### 当以下情况成立时，优先 Graphviz 或其他布局引擎

- 图规模更大；
- 自动边路由很重要；
- 布局质量比编写便利性更重要。

### 当以下情况成立时，优先专业工具/静态分析输出

- 需要精确 CFG、AST、dataflow、call graph 或 dependency 事实；
- 图由机器生成；
- 源码级精度比人工整理后的可读性更重要。

### 当以下情况成立时，优先表格或正文

- 关系图非常小；
- 节点很多但语义很简单；
- 图只是在重复正文。

### 当以下情况成立时，优先手工编辑的图

- 精确的视觉构图本身就是解释的一部分；
- 要求出版级布局；
- 形式化记法或几何关系很重要，而所选 Renderer 无法保持这些语义。

## 粒度

核心视图目标：大约 5–12 个主要节点。大型图应拆分为 context/core/detail 视图，而不是把所有标签不断缩小。

## 图 / 文本 / 代码分工

```text
图   → 空间/时间关系
正文 → 语义、条件、后果
代码 → 证据与导航
```

## Mermaid 永远不是语义权威

Mermaid `flowchart` 可以绘制经过整理的控制视图，但不能因为它看起来像 CFG，就称其为正式 CFG。语义模型必须独立于 Renderer 的语法。
