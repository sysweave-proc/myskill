# 架构重构方法

## 目的

当目标是一个大型既有系统，而其架构只得到部分文档化，或者“实际构建出的架构（as-built）”可能与预期设计不同的时候，使用架构重构。

## 方法

```text
1. 形成架构假设
2. 收集源码事实
3. 提取架构候选项
4. 聚类 / 聚合
5. 重构场景和运行时路径
6. 将高层元素映射到源码证据
7. 将模型与源码进行对比
8. 细化模型
```

## 自顶向下 + 自底向上

### 自顶向下输入

- 官方项目文档；
- 设计文档；
- 公共 API 与子系统描述；
- 构建/模块边界；
- 已建立的术语体系。

这些输入形成的是**架构假设**，而不是证明。

### 自底向上输入

- 符号引用；
- 调用/依赖图；
- AST 信息；
- 数据流/控制流证据；
- 生命周期模式；
- 运行时入口点；
- 同步与资源 ownership。

这些输入提供源码证据，用于验证或修正架构假设。

## 发现架构主干

从 5–12 个具有明确职责和稳定接口的高层元素开始。

避免：

- 每一个源码目录；
- 每一个库依赖；
- 每一个后台 worker；
- 每一个辅助函数。

## 发现关键路径

选择能够穿过多个子系统的代表性场景。典型类别：

```text
请求/查询路径
事务路径
数据读取路径
数据写入路径
恢复路径
后台维护路径
启动/关闭路径
```

Critical Path 是一等知识对象，因为它把原本彼此孤立的子系统连接起来。

## 映射

使用显式映射模型：

```yaml
mapping:
  high_level_element: "Buffer Manager"
  source_symbols: ["BufferDesc", "ReadBuffer_common", "BufferAlloc"]
  source_paths: ["src/backend/storage/buffer"]
  runtime_paths: ["Page Read Path"]
  evidence: []
```

## 细化规则

当源码证据与架构文档冲突时，不要静默地选择其中一个。记录：

```text
意图 / 文档化架构
vs
实际构建出的行为
```

然后判断差异属于：

- 实现细节；
- 架构漂移；
- 过时文档；
- 尚未解决的歧义。

## 架构重构反模式

- 把目录树当成架构；
- 一张巨型架构图；
- 仅凭命名推断架构；
- 第一版架构形成后就冻结；
- 没有场景验证的架构结论。
