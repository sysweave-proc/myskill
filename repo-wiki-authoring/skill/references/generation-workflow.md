# 生成流程：从零产出任意仓库的 repo wiki

> **目标**：给定**任意**代码仓库，产出一套可导航的"架构/系统设计文档"。
> **规模标杆**：一个大型 C++ 仓库的实测产出为 **211 篇 content + 5 张主题卡 + 1 棵 14 模块的模块卡树**（下文的目录名/类型名均取自该样例，仅作示意）。

---

## 步骤 1：扫描与量化

- 列出顶层目录，统计每个目录的文件数/代码量，识别"大类"（构建、客户端、服务端、存储引擎、插件、组件、基础库、测试、打包…）。
- 记录语言与构建系统（CMake/autotools/Bazel…），它们是 `技术栈.md` 的证据。
- 产出：一份"目录 → 规模 → 疑似职责"的清单，作为模块划分原料。

## 步骤 2：模块建模（knowledge 的基础）

把仓库切成**模块树**：
- 一个顶层目录 = 一个模块；`scope` = 它的目录清单。
- 判断 `depends_on`（单向依赖）与 `related_to`（协作）。
- 根模块 = 仓库根（`module_path: ""`，scope 是根级配置文件如 `CMakeLists.txt`、`README`、`configure.cmake`）。
- 为每个模块生成：`_module.yaml` + `概述/技术栈/架构设计/特殊配置与命令/编码规范` 五件套。
- 最后汇总 `_index.yaml`。

**判据**：一个模块的 `架构设计.md` 写完，读者应能说出该目录"有哪些子目录、各干什么、依赖方向朝哪"。

## 步骤 3：规划两棵目录树

### 3a. content 树的规划规则

- 分**大主题**：按目标仓库的领域切（样例仓库切出的是 核心架构 / SQL处理 / 存储引擎 / 事务系统 / 并发控制 / 连接管理 / 复制和高可用 / 内存管理 / 文件系统I/O / 网络通信 / 插件系统 / 客户端工具 / API参考 / 安全机制 / 监控和诊断 / 配置管理 / 部署和运维 / 故障排除 / 快速开始 / 项目概述 / 开发者指南）。
- 每个大主题下再分**子系统页**，必要时 3~4 层（`核心架构/SQL层架构/查询优化器/范围优化器.md`）。
- 每层目录配一个同名"总览页"（`存储引擎/存储引擎.md`、`核心架构/核心架构.md`、`SQL处理/SQL处理.md`）——**总览页负责索引子页，子页负责细节**。
- 每篇一个**叶子主题**；粒度标准："一个能独立讲清的子系统/机制"。太大就拆（查询优化器拆出连接优化器/范围优化器/成本模型/查询重写）。
- 顶层还放若干**横向导航页**（项目概述 / 快速开始 / 开发者指南 / 部署和运维 / 故障排除），面向不同读者层。

### 3b. 为每一页写"生成指令"（这是可复刻的关键）

每页在元数据里对应 `(prompt, dependent_files)` 一对：

```json
{
  "name": "range-optimizer",
  "description": "范围优化器",
  "prompt": "创建范围优化器的详细技术文档。深入解释范围分析（get_mm_tree）如何把 WHERE 条件转为 SEL_TREE/SEL_ROOT/SEL_ARG 区间图；说明单键范围、索引合并、跳过扫描、分区裁剪各自适用场景与成本估算；给出关键时序图与不同索引策略的对比；包含 EXPLAIN 与 Opt_trace 的诊断方法。",
  "dependent_files": "sql/range_optimizer/,sql/range_optimizer/tree.h,sql/range_optimizer/index_merge.h",
  "progress_status": "completed"
}
```

规则：
- `prompt` 必须写清三层：**要解释什么机制** + **必须覆盖的要点（3~6 个，动词开头）** + **要求哪些图/对比/诊断**。它同时是"取景框"，防止写飞。
- `dependent_files` 是**取证清单**，逗号分隔，可给目录；写页面前必须按它读源码。
- `progress_status` 走 `pending → generating → completed`，支持断点续做。

## 步骤 4：逐页取证 + 按模板写作

对每一页：
1. 按 `dependent_files` `read_file` / 搜索真实源码——**不凭记忆写**。
2. 抽取：目录与文件职责、关键类与函数、关键数据结构、关键行号区间（粗区间即可）。
3. 套 `content-page-template.md` 的 10 节骨架（或 `knowledge-card-template.md`）。
4. **每写一张图就立刻回填 `图表来源`，每写完一节立刻回填 `章节来源`**——不要留到最后补。

### 4b. 批量调度：并发宽度与存档点（防"整轮中断"）

步骤 4 要重复上百次，是全流程**唯一会把平台请求打爆**的地方。限流（HTTP 429 / "model access restricted"）的代价不是"少写一篇"，而是**整轮长跑中断**——已经生成的上下文全部作废。可控的只有三件事：

- **压并发宽度，而不是"整体慢一点"**：一个回合内不要堆几十个并行 `read_file` / 并行子任务；按 **1~3 篇一批**串行推进，批与批之间落盘一次。（agent 无法测量请求速率、也没有"延迟发送"的手段，"少开并发"才是它唯一能执行的降速动作。）
- **落盘 = 存档点**：每页写完**立刻写文件 + 更新 `progress_status`**，不要攒在对话里最后统一落盘。中断后从 `pending` / `generating` 续做，已 `completed` 的页不重跑——这正是该字段存在的理由。
- **被限流时的正确反应**：停下当前批 → 退避后再试**同一批**（没有等待手段时向用户报告、下一轮继续，**不要立刻原地重试**）→ 重试前先确认上一批已落盘。**绝不能把"请求失败"登记成 `completed`**：污染进度状态比慢一小时代价大得多。

## 步骤 5：总览页与元数据

- 写一份 `wiki_overview`（`<blog>` 包裹的整体分析：项目介绍 / 技术架构 / 关键实现 / 关键特性 / 项目结构分析 / 结论与建议 / Sources）。
- 落盘 `metadata.json`：`wiki_repo`（目录树快照 + 状态）、`wiki_overview`、`wiki_catalogs[]`（每页的 prompt/dependent_files）、`wiki_items[]`（目录项）、`knowledge_relations[]`（`PARENT_CHILD` 父子关系）。
- 产物目录：`<wiki_root>/<locale>/content/**` 与 `<wiki_root>/<locale>/knowledge/**` 与 `<wiki_root>/<locale>/meta/**`，另有 `knowledge/<locale>/_index.yaml`。

> mysql-server 的 `repowiki-metadata.json` 里 `current_document_structure` / `catalogue_think_content` 是**加密**的（`WikiEncrypted:` 前缀），说明生成器内部保留了"规划过程"但对外不外泄；复刻时用普通 JSON 落盘即可。

## 步骤 6：校验清单（交付前逐条过）

**结构**
- [ ] 每个顶层目录都有对应模块卡与至少一篇 content 页（地图无洞）。
- [ ] content 每篇含 `<cite>` + 10 节（序号 1~10）+ 结论 + 附录。
- [ ] 目录锚点与正文标题**逐字一致**（`## 性能考量` ↔ `#性能考量`）。
- [ ] 主题卡 frontmatter 五字段齐全（`kind/name/category/scope/source_files`），section 3/4 名称固定。

**溯源**
- [ ] 每张 mermaid 后有 `图表来源`，每个实质小节后有 `章节来源`。
- [ ] 所有坐标形如 `[path:start-end](file://path#Lstart-Lend)`，路径相对仓库根，且标签数值与 URL 片段**逐字一致**。
- [ ] 每个坐标**回源核对过**：文件存在 + `end ≤ 文件实际行数`（`wc -l`）。粗区间不等于可以越界，`#L1-200` 指向几十行的文件是死锚点。
- [ ] 无源码可引的小节以 `[本节为…，不直接分析具体文件]` 收尾。

**图表**
- [ ] 图型与问题匹配（分层 graph TB / 时序 sequenceDiagram / 决策 flowchart / 继承 classDiagram / 依赖 graph LR）。
- [ ] 单图视觉节点 5~7 个，节点内不堆字段。
- [ ] 没有"需要大段注释才看懂"的图（有就拆）。

**一致性**
- [ ] 术语全文统一（如 handler/handlerton、THD、AST、PSI 首次出现给全称）。
- [ ] 交叉引用与目录层级不脱节（总览页必须能指向其所有子页）。

## 规模基准（用于估算工作量）

| 指标 | 大型仓库实测（示例） |
|---|---|
| content 页数 | 211（另有 2 篇根级导航） |
| content 目录层级 | 最深 4 层（`核心架构/插件系统架构/服务插件/基础设施服务/`） |
| 主题卡 | 5 张（构建/依赖/日志/配置/错误处理） |
| 模块卡 | 14 个模块（根模块 + 13 子模块） |
| 单页 mermaid 数 | 3~8 张（平均 5） |
| 单页行数 | 约 100~400 行 |

## 与源码笔记的边界（务必守住）

| | repo wiki（本技能） | 源码笔记（仓库自带 AGENTS.md） |
|---|---|---|
| 方向 | 自上而下，先地图后细节 | 自下而上，先心智模型后实现 |
| 单位 | 子系统 / 横切主题 | 单一机制 |
| 坐标 | 粗区间（`#L24-123`，须落在文件行数内） | **file + 符号名** + 真实调用链（行号非必需） |
| 回答 | 这块代码干什么、数据怎么流 | 为什么这样设计、每一步发生什么 |
| 图 | mermaid（分层/时序/状态/依赖） | 数据流图、状态机、调用链树 |

**同一事实只在一个地方展开**，另一处用链接/坐标回指。
