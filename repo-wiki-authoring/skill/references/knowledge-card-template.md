# 模板 B：`knowledge/**` 知识卡

> **适用**：任意大型代码仓库的"专题切片"。与语言/项目无关。
> **定位**：`content/**` 是"按子系统分的地图"，知识卡是"按横切主题切的切片"——粒度不同、互补。
> **示例来源**：下文的 MySQL 类型名、文件路径仅作示意，写到别的仓库时全部换成该仓库的对象。
> **两类知识卡**：**主题卡**（一个横切主题一篇 md）与**模块卡**（一个仓库模块一个目录，5 个固定文件）。

---

## 一、`_index.yaml` — 顶层索引（每个 knowledge 根一份）

```yaml
# 知识卡导出索引文件
schema_version: 1
locale: zh-CN
branch: <源码仓库分支名>
nodes_managed: true
exported_at: "<ISO8601>"
modules:
    "<module_key>":                # 英文 key；根模块用空字符串 ""
        dir_name: <目录名（中文）>
        title: <中文标题>
        scope:                     # 该模块覆盖的目录/文件
            - sql/
        source_files: []
        children:                  # 子模块 key 列表（构成模块树）
            - storage_engines
        depends_on: []
        related_to:
            - path: <其他 module_key>
```

## 二、`_module.yaml` — 每个模块目录一份

```yaml
schema_version: 1
module_path: sql_server        # 根模块为 ""
title: MySQL 服务器核心 SQL 引擎
scope:
    - sql/
source_files: []
depends_on: []
related_to:
    - path: storage_engines
```

模块划分原则：**一个顶层目录 = 一个模块**；`scope` 就是它的目录清单；`related_to` 记协作（不是依赖）关系，`depends_on` 记单向依赖。子模块（如 `sql/` 下的领域）可继续嵌套成树。

## 三、模块卡：5 个固定文件

目录形态：`knowledge/<locale>/<模块中文名>/` 内含 `_module.yaml` + 下列 5 个 md。
每篇都**短**（几十字到一段），目标是"不看源码就能说清这个模块是什么"。

| 文件 | 长度 | 写什么 |
|---|---|---|
| `概述.md` | **一句话** | 该模块"做什么"，罗列它涵盖的功能域 |
| `技术栈.md` | 一段 | 语言、生成器（bison/flex）、框架（Component Framework）、数据格式（SDI）、构建期产物 |
| `架构设计.md` | 一到数段（可 bullet） | **目录/子目录 → 职责** 的映射，最后给依赖方向（自上而下：命令→优化器→执行器→抽象→插件） |
| `特殊配置与命令.md` | 一段 | 构建期开关、编译期生成的文件、必须手动运行的生成器/脚本 |
| `编码规范.md` | 3~6 bullet | 该模块内部的**惯例**：命令如何建模（`Sql_cmd_*`）、插件如何接入（继承基类+能力位标志）、类型如何分头文件、错误文本如何集中 |

写法要点：
- `概述.md` 严格一句话，不换行、不分点（例：`实现 MySQL 服务端的核心 SQL 引擎，涵盖…全部服务器端功能。`）。
- `架构设计.md` 用 `` `文件名` `` 内联标注路径，不要求行号；面向"这个目录里有什么、谁调谁"。
- `编码规范.md` 是**本模块专属惯例**，不要写通用 C++ 规范。

## 四、主题卡：YAML frontmatter + 4~5 节

目录形态：`knowledge/<locale>/<主题中文名>/<主题中文名>.md`（目录名与文件名同名）。

```markdown
---
kind: error_handling                 # 机器可读主题 key（snake_case）
name: MySQL 错误处理体系：Diagnostics Area、Internal_error_handler 与 ER_* 错误码
category: error_handling             # 通常与 kind 相同
scope:
    - '**'                           # 横切主题覆盖全仓库
source_files:                        # 本卡取证所依据的源文件（相对仓库根，含头文件）
    - sql/sql_error.h
    - sql/sql_error.cc
    - sql/error_handler.h
    - include/errmsg.h
    - mysys/errors.cc
---

## 1. 总体方案
<3~4 个 bullet 分层叙述"这套东西由哪几层/哪几个子系统构成"，每层点名 文件（无行号）>
1. **<层名>层**（`path/file.cc`）：<职责与关键函数>
2. **<层名>层**（`path/file.h`）：<职责与关键类型>
3. **<层名>层**：...

<可选：一段补充"此外，X 提供…，Y 中 Z 演示了…">

## 2. 关键文件与包
<表格（列名可微调：路径|作用 / 文件|职责）：
| 路径 | 作用 |
|---|---|
| `a.h` / `a.cc` | <关键类型 + 关键函数> |
| `b.h` | ... |
（也可用 bullet 形式：`- 顶层入口：`f1`、`f2``）>

## 3. 架构与约定
<分点讲机制约定，每条都要有"为什么"/语义边界；机制复杂时开 ### 3.1 / 3.2 … 子节（如启动顺序、搜索策略、来源追踪、特殊前缀、分隔符机制、统一模式）>

### 3.1 <子机制>
### 3.2 <子机制>

## 4. 约定与约束
<禁止项 / 必须项 / 边界条件 / 安全约束 / 优先级顺序 / 向后兼容注意点。每条一句，可带 `path:行号` 精确引用（此处允许精确行号，与 content 页的粗区间不同）>

## 5. 适用性说明          ← 可选
本仓库是 <项目>，<主题> 是核心基础设施之一，贯穿 <范围>，证据充分（`f1`、`f2`、`f3`），因此本类别适用且置信度为 high。
```

**节标题允许的变体**（保持一、二节"先总后表"的语义即可）：

| 节 | 允许标题 |
|---|---|
| 1 | `总体方案` / `使用的系统与框架` / `使用的系统与总体方法` / `构建系统总览` |
| 2 | `关键文件与包` / `关键文件与职责` / `关键文件与模块` / `关键文件与位置` |
| 3 | `架构与约定`（固定） |
| 4 | `约定与约束`（固定） |
| 5 | `适用性说明`（可选，仅横切主题卡用） |

与本仓库源码笔记的差别：主题卡**不画 mermaid、不讲调用链**，只给"分层构成 + 文件职责表 + 约定/约束"，行号引用是**精确**的（`mysqld.cc:7472-7479`）。它是"专题索引卡"，不是"机制讲解"。
